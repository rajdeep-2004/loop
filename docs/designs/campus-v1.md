## Problem Statement

University life runs on tools that know nothing about the university. Students sit in dozens of
WhatsApp groups, clubs live on Instagram pages and invite links, and official notices arrive by
email to everyone or to nobody. Three things are hard as a result:

1. **Finding people.** There is no directory. A student cannot answer "who in 3rd year is
   interested in AI?" without asking around.
2. **Finding clubs.** A club is invisible until someone forwards an invite link. A student cannot
   see what a club does, who is in it, or what it is working on before joining.
3. **Getting relevant information.** An announcement for 2nd-year technology students goes to a
   group that also contains everyone else, or it never reaches them.

Campus is a mobile app that ties chat to the university's own structure (schools, programs, years,
classes, clubs), so that people, clubs and announcements are discoverable and addressable through
that structure. `chat-app-idea.md` is the feature brief. Its "Campus V1" list is the scope.

## What Makes This Cool

- **The club walk.** Discover a club, read its public page, see its members, join, land in the
  private club chat, open a member's profile, message them. One continuous path that no single
  existing app gives a student.
- **Announcements with an audience.** A club or the university sends a notice to "School of
  Technology, 2nd and 3rd year" and only those students get it, live. WhatsApp and Discord
  cannot do this because they do not know who is in which school or year.
- **Identity for free.** Every profile already carries school, program, year and class, so
  Discover can filter by them from day one.

## Constraints

- **Purpose:** university capstone prototype, built to be showcased. Not a production service.
- **Builder and time:** solo, about 6 to 8 weeks.
- **Platform:** mobile app.
- **Stack requested by the builder:** TypeScript and MongoDB on the backend. Fastify on Node is
  acceptable. Redis is optional.
- **Scale:** explicitly not a goal. One server process, one database, seeded demo data.
- **Scope:** every item in the idea doc's "Campus V1" list. No cuts.

## Premises

1. Every feature in the idea doc's V1 list gets built, in milestones ordered so the app is
   demoable after each one.
2. One university instance with seeded demo data. No multi-university support.
3. Identity is email and password signup, with school, program, year and class picked during
   onboarding. No university SSO and no ID verification.
4. The client is a mobile app (changed from "responsive web" during the session). Messages and
   announcements arrive in-app in realtime. Push notifications are a non-goal.
5. A university admin role posts university announcements. Club owners and admins post club
   announcements. Both can target by school, year and program/class.
6. Scalability is out of scope. Choices favor the fewest moving parts.

## Approaches Considered

### Approach A: Lean (chosen)
Expo (React Native) app, one Fastify server that serves both the REST API and Socket.IO, MongoDB.
Presence and typing state live in server memory. Fewest moving parts, fastest path to a demo on a
real phone. Cannot run on more than one server, which does not matter for a prototype.

### Approach B: Full
Same app, plus Redis for presence, typing and rate limits, a background worker for announcement
fan-out and push notifications, and S3-style object storage. Ruled out: the builder wants a
minimal prototype and no scalability work.

### Approach C: Next.js API routes plus a hosted realtime service
Ruled out: Next.js adds little as an API-only backend for a mobile app, and a hosted realtime
vendor outsources the main engineering of a chat app.

## Recommended Approach

Approach A. Wireframe: none (skipped to keep the session short).

### Visual direction

The builder's brief: the UI must be "really interesting and sexy", with no generic UI. The
direction is neo-brutalism (assumed meaning of the builder's word "Bootlegism", to be confirmed):
thick black outlines, hard offset shadows with no blur, flat saturated color blocks, oversized
bold type, and visible structure instead of soft cards and gradients. Each school gets its own
color, which appears on profiles, avatar rings and announcement audience tags, so the
university's structure is visible at a glance. This is a product requirement on the same level
as the features: a design system (colors, type, spacing, core components) is built in M1 before
any screen, and `/design-consultation` runs before M1 to fix it in a `DESIGN.md`.

### Stack

| Layer | Choice | Why |
|---|---|---|
| Mobile app | Expo (React Native), TypeScript, Expo Router | One codebase for Android and iOS, runs on a phone through Expo Go during development |
| Server state on the client | TanStack Query | Caching, pagination and loading/error states without hand-written plumbing. The builder first asked to drop it, then confirmed it stays |
| Realtime | Socket.IO (client and server) | Reconnection, rooms and acknowledgements built in |
| API | Fastify on Node, TypeScript, Zod schemas | Requested by the builder; thin handlers, validated input |
| Database | MongoDB with Mongoose | Requested by the builder; document model fits messages and profiles |
| Auth | Email + password (hashed), JWT access token + refresh token, tokens stored in the device's secure storage | Simple and standard for a mobile client |
| File storage | Behind a small storage interface; local disk on the server to start | Hosting choice is open (see Open Questions) and the interface keeps a later swap to a hosted bucket cheap |
| Redis | Not used | The builder said to include it only if needed. With one server process, presence, typing and rate limits fit in memory, so it is not needed. It becomes needed only if the API ever runs as more than one process |
| Next.js | Not used | No web client; adds nothing as an API host |

Repo layout: one repository with `apps/mobile`, `apps/api` and `packages/shared` (Zod schemas and
types used by both sides).

### Data model (MongoDB collections)

| Collection | Key fields | Notes |
|---|---|---|
| `schools` | name, description | Seeded |
| `programs` | schoolId, name, years | "Course / Program" in the idea doc. Seeded |
| `users` | name, username (unique), email (unique), passwordHash, avatarUrl, bio, schoolId, programId, year, classSection, skills[], interests[], role (`student` or `university_admin`) | Lowercased copies of name and username are indexed for prefix search; skills and interests are indexed arrays of lowercase tags |
| `clubs` | name, slug (unique), bannerUrl, description, whatWeDo, currentlyWorkingOn, nextEvent {title, startsAt}, conversationId | Public page fields come straight from here. The member count is not stored; it is counted from `clubMemberships` when the page loads, so it can never drift |
| `clubMemberships` | clubId, userId, role (`owner`, `admin`, `member`) | Unique index on (clubId, userId) so a double tap on Join cannot create two rows |
| `conversations` | type (`dm`, `group`, `club`), dmKey (sorted pair of user ids, DMs only), name, description, imageUrl, clubId, lastMessageAt | dmKey guarantees one DM per pair of students. Its unique index is a partial index that applies only where type is `dm`, because group and club conversations have no dmKey and a plain unique index would reject the second one |
| `conversationMembers` | conversationId, userId, role (`admin`, `member`), lastReadMessageId | Unique index on (conversationId, userId). Drives unread counts and read status |
| `messages` | conversationId, senderId, clientMessageId, type (`text`, `image`, `file`), body, attachments[], replyToId, threadRootId, threadReplyCount, reactions[{emoji, userIds[]}], editedAt, deletedAt | Index on (conversationId, _id) for paging. Unique (senderId, clientMessageId) so a retry never duplicates a message |
| `announcements` | source (`university` or `club`), clubId, authorId, title, body, audience {schoolIds[], years[], programIds[], classSections[]}, createdAt | Each empty audience array means "no restriction on this dimension"; all four empty means everyone. No per-user copies are stored |

### How the main pieces work

- **Sending a message.** The app generates a `clientMessageId`, shows the message immediately as
  "sending", and emits it over the socket. The server validates membership, saves it, acknowledges
  to the sender ("sent") and delivers it to the personal socket room of every current member of
  the conversation. If the app retries after
  a dropped connection, the unique index returns the already-saved message instead of a duplicate.
- **Message status.** Two states: sent (server acknowledged) and read (the other member's
  `lastReadMessageId` has passed it). In groups and clubs only "sent" is shown.
- **Presence and typing.** The server keeps a map of user id to open socket count in memory.
  Online or offline changes and typing events are relayed over sockets and never stored.
- **Reply vs thread.** `replyToId` is a quoted reply inside the main chat. `threadRootId` moves the
  conversation into a side thread; the root message shows "N replies" from `threadReplyCount`.
- **Edit, delete, reactions.** Only the sender edits or deletes. Delete is a soft delete that
  leaves a "message deleted" placeholder. A reaction is one emoji per user per message, toggled.
- **Socket authentication.** The app passes its access token in the Socket.IO handshake. The
  server verifies it, attaches the user id to the socket and joins the socket to one personal room,
  `user:<id>`. There are no per-conversation rooms. Every delivery looks up the conversation's
  current members in the database and emits to each member's personal room, so a student who just
  joined a club, was added to a group or received a first DM gets messages live with no
  reconnect, and a student who left or was removed stops receiving them immediately. An invalid or expired token is rejected with a defined
  `auth_expired` error; the app then refreshes its token over REST and reconnects. A
  reconnect needs no room bookkeeping beyond rejoining the personal room.
- **Clubs.** Joining creates a membership row, and only if that insert succeeds, a conversation
  member row. Leaving deletes both. The member count is counted from memberships, never stored.
  The public page is readable by any signed-in student; the club chat only by members. Owners
  and admins edit the page, manage members and post announcements. The owner cannot leave until
  ownership is transferred to another member; admins and members can leave freely.
- **Groups.** The creator is the first admin. Admins add and remove members, promote and demote
  admins, and edit the name, description and image. Any member can leave. If the last admin
  leaves, the longest-standing remaining member becomes admin. A group with no members is deleted.
- **Announcements.** No fan-out. A student matches an announcement when every non-empty audience
  array contains the student's value for that dimension: AND across school, year, program and
  class, OR within one array. So "School of Technology, years 2 and 3" reaches only students who
  are in that school and in year 2 or 3. The same rule is used for the feed query and for the
  live socket push on creation. Club announcements are public outreach: they reach every student
  who matches the audience, member or not (the idea doc's example is a workshop invite), and they
  also appear on the club's public page. The feed query is therefore the same for both sources.
- **Discover.** Name and username use a case-insensitive prefix match on the indexed lowercase
  fields, so typing "raj" finds "Rajdeep". Skills and interests are an exact tag match. School,
  program and year are filters. Clubs browse and search. Schools list with their programs and
  students. All lists are paginated.
- **Media.** Two kinds of upload, both through the API, both stored under a server-generated
  random name (the uploaded filename is kept only as a display label). Public images (avatars,
  club banners, group images): JPEG, PNG or WebP up to 5 MB, readable by any signed-in student.
  Chat attachments: the same image types up to 5 MB, and PDF, DOCX, PPTX, XLSX, TXT or ZIP up to
  20 MB. Chat attachments are read through an authenticated route that checks the requester is a
  member of the conversation, so a link from a private chat is useless to anyone else. Images
  render inline; files show name and size and open on tap.

## Open Questions

   service. This decides file storage (local disk vs a hosted bucket). To be settled in the
   Delivery setup step.
2. **Who can create a club?** Assumed: any student, who becomes its owner. Alternative: only the
   university admin.
3. **What is a "class"?** Assumed: a section label within a program and year (for example
   "CSE-A"), picked from a seeded list.
4. **Do threads exist in DMs?** Assumed: no, only in group and club chats, where clutter is real.
5. **Should signup be limited to a university email domain?** Assumed: no, since the demo uses
   seeded accounts.
6. **Product name vs repo name.** The idea doc says "Campus", the repository is "loop".
7. **Visual direction.** "Bootlegism" was read as brutalism (neo-brutalist style). Confirm, or

  clubs with filled-in pages and chat history.

### R3-2 — completeness (minor)

**Problem**

> Persisting from R2-4. Join is two ordered writes without a transaction. If the membership insert succeeds and the conversation member insert fails, the student is a club member with no access to the club chat.
